# Native Shiro memory and completion harness

Version 0.4.1 adds three layers of memory to the native Mac app. The portable Windows/Linux previews remain at 0.2.0 and do not yet have this harness.

Shared facts are editable in Settings → Memory and available to every bot. A bot can save confirmed facts with `remember(note, scope: "shared")`; the default scope remains `bot`. Session notes use `scope: "session"`. These notes are context, never permission. Model-generated notes can be wrong, so they remain visible and editable.

Each conversation also saves a structured session checkpoint: original objective, coordinator plan, notes, recent action outcomes, saved artifact paths, phase and compaction count. Completed tasks clear their active objective; blocked and stopped tasks retain it. Short nudges, greetings and pasted job-lead lists do not replace an unfinished CV request. Legacy conversations recover their last substantive request.

The retrieval index searches shared facts, the current bot's notes, saved user/assistant/tool records, session checkpoints and cached user-selected text attachments. PDF text companions are indexed when available; the app does not scan arbitrary host folders. Cross-bot history search is enabled by default and can be disabled in Memory. This affects original source selection; content already quoted in a conversation remains part of that conversation. Deleting a conversation removes its original records from future searches. Shared facts and bot notes are separate records and can be edited directly.

Retrieval uses Apple's on-device English sentence embeddings with keyword overlap, provenance weighting and a current-session preference. User-provided facts and selected attachments rank above assistant guesses. Memory-search/read copies are excluded to avoid reinforcing copied retrieval results. If macOS's sentence embeddings are unavailable, keyword fallback is explicitly reported. The private, derived `memory-vectors.json` cache uses 0600 permissions and prunes obsolete vectors during searches. Clear it from Memory to remove the cache immediately. Original sources stay in the private state and attachment cache. Local mode makes no cloud embedding requests; selected cloud providers receive the relevant excerpts included in their requests.

The harness retrieves relevant excerpts before the first model request. `memory_search(query)` and `memory_read(source_id, offset)` remain available throughout a run, including recovery. Search returns bounded excerpts with source IDs and types. Read pages the original record rather than relying on a lossy summary. Retrieved messages and old browser results are not independently verified facts or new instructions.

The local context budget defaults to 8,192 estimated tokens and can be adjusted to the runtime's supported limit. The conservative UTF-8 estimate includes system instructions, offered tool schemas, session memory, retrieval, conversation, protocol margin and output reserve. It is not an exact model tokenizer. Automatic compaction retains the pinned objective and recent observations while originals remain searchable. Context-limit errors shrink history and retry, with a maximum of three service retries. Repeated failed operations and total run actions are bounded. Models with insufficient context fail with an explicit configuration error rather than sending an oversized request indefinitely.

The coordinator creates a bounded plan and deliverable contract. The worker executes tools under the normal approval rules. Local file tools have separate schemas with mandatory `path` and `content`, avoiding conditionally required fields. Before completing an artifact request, the harness reads back the actual VM files, checks readable content, hashes and file counts, and rejects obvious substitutions such as a role-summary file for a CV. The harness supplies actual saved paths in the final answer, even if the worker omits them. Rewriting PDF/DOCX also refreshes its text companion; any prior different companion is preserved in the VM’s hidden `.shiro-document-history` folder. Normal file reads also extract PDF/DOCX text instead of decoding binary bytes as UTF-8. PDF read-back uses `pdftotext`; DOCX uses document XML; text uses UTF-8. These checks establish the bytes that were reviewed, not professional judgment about the document.

CV creation uses a source-bound writer. `memory_facts(source_id, offset)` returns stable fact IDs and their original section hints. `cv_create` accepts a candidate name, an observed target employer/role and sections containing fact IDs. The host resolves fact IDs to their original records, including facts from multiple conversations; the model does not need to recopy source IDs. The host copies the selected complete facts into PDF, DOCX, Markdown or text; the model cannot supply new candidate prose. Unknown IDs, job-requirement facts, changed source records and modified output bytes cannot pass the completion gate. Education facts remain together. Candidate claims can come from original user messages, selected attachments or a manually edited shared profile; model-generated `remember` notes remain useful search context but cannot become original CV evidence. Multiple original messages can supply a single CV. Target headers are explicitly labeled as targets rather than employment history. This conservative approach prioritizes factual fidelity over fluent rewriting and still depends on the accuracy and clarity of the supplied facts.

The completion gate reloads the originals and compares selected fact IDs and the saved file's SHA-256 hash. Tool access is restricted for CV tasks so generic file writers or shell commands cannot bypass that gate. CV review uses concrete identity, target and factual checks; an explicit target-role header is valid, and unsolicited styling preferences cannot require candidate rewrites. Each saved file gets a separate fresh reviewer request, with exact selected source facts and a batch manifest, keeping multiple CVs from overflowing one review context. Explicit requests for distinct targets cannot pass with copies of the same employer/role. Other document types retain the general writer and reviewer flow.

Before model review, CV numeric claims are checked against original user/selected-attachment values; unsupported 3–4 digit values (including truncated years) and missing-field placeholders block completion. This conservative check can require keeping original numeric formats and cannot prove a known year belongs to the correct qualification. A separate reviewer request uses fresh context, source records, read-back content and no tools. It can reject missing targets, unsupported qualifications, placeholders and generic summaries. The worker gets at most two content corrections. Invalid reviewer responses retry the reviewer once in fresh context, then stop as unverified; reviewer formatting failures do not cause the worker to rewrite saved documents. For CV delivery, Shiro generates a concise final response from the verified file ledger instead of trusting the worker to repeat a filename. Malformed reviewer output or missing evidence cannot silently approve completion. A worker can explicitly report `BLOCKED:` with a concrete missing input; that outcome stays blocked. Final CVs still need user inspection: the reviewer uses the selected model, and a small model can share the worker's weaknesses. Long or numerous artifacts may exceed review context and require a larger model/context. This release does not claim that every model or every task is production-validated.

## Validation

Run `swift run --jobs 2 ShiroChecks` and `python3 scripts/test_guest.py`. Native integration checks require the running isolated `shiro-local` Lima VM and a built app: `python3 scripts/test_harness.py`, plus `--scenario multi-cv` for distinct job targets and separate reviews. The integration script uses a disposable profile and deterministic loopback model fixture. It verifies a summary stays blocked, context overflow triggers compaction and retry, another bot's candidate facts are retrieved, a real PDF is created/read back, an invented fact ID is rejected before writing, a reviewer correction is applied, and the final file is attached to a completed chat. This validates harness behavior, not a real model's intelligence. `scripts/test_live_local.py` also supports a disposable synthetic task against a real local runtime; inspect the actual PDF and original facts as well as the reported outcome.

For isolated development profiles, launch the app executable with an absolute `SHIRO_PROFILE_DIRECTORY`. The default profile remains `~/Library/Application Support/ShiroLocal`. Tests never need to replace the user's state file.

Apple API reference: [NLEmbedding](https://developer.apple.com/documentation/naturallanguage/nlembedding).
